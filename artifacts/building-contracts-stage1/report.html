Implemented contracts and presentation

Contracts, projection, request ownership, return state and disabled handoff builder, and focused UI are isolated under experimental paths.

  • The catalogue contains authorised building identifiers, names and addresses only. Operational input is explicitly one building, with immutable unit and sale-attempt IDs; identity, role, organisation and access revision are part of the response scope. Related terms, documents, payments and floor data are checked before projection. Portfolio and unrelated module input are rejected.
  • The wire projection includes permitted buyer labels, stage, all permitted actions, responsibility, real deadline facts where supplied, source completeness and an as-of time. It does not serialise broad dashboard inputs, raw histories, signed document URLs or credentials.
  • Existing pure responsibility, classification, permission, calculation and floor-order helpers are reused. Building appointment owns agent/conveyancer work; internal work stays with the developer team. Actor/editor names never assign work. Access, ownership and capability are separate.
  • Missing appointment is Unallocated; unavailable appointment input makes counts incomplete. Two people in the same organisation see the same team work; another organisation with the same role does not inherit ownership. Existing role-level on-behalf capability is displayed only as disabled secondary information. Existing record/backend checks still govern any future action.
  • Actions retain distinct IDs even when their destination is shared. Primary presentation prefers our work, then existing register dependency order, fee/urgency/date order and stable IDs. Queue filters match any action without hiding other action titles or teams. Financial/reconciliation warnings stay alongside the row.
  • Developer waiting defaults show read-only reservation/invoice context. They do not mount another party's form. A queried legal task uses a role-appropriate heading; the conveyancer preview says “Resolve the query”, while another team's query is labelled as waiting. Detailed task forms remain outside this pilot.
  • Abort plus generation and scope checks reject late success, error and completion effects, including A→B→A. Scope changes clear prior rows/counts immediately. Dashboard→worklist reuses one scoped snapshot. No speculative prefetch or other-building detail read exists.
  • Tab-local session storage holds only filters, page and scroll, keyed by identity, role, organisation, access revision and building. URLs retain building/unit/attempt identity. Changing building from a record returns to the destination worklist, never the same label. Known scope/revision changes invalidate snapshots; real auth subscription and logout storage cleanup remain Stage 2 work.
