3. Changes required for the first integration

  • Entry and shell: reuse existing verified session and building-access rules. The chooser needs authorised building metadata only. One accessible building enters directly; several require explicit choice on a fresh homepage. A URL retains a workspace on refresh. No global “last building” silently redirects a new entry. Unit destinations appear only after opening a unit.
  • Scoped read projection: a proposed additive pilot read contract accepts exactly one building ID, validates caller access before and after loading, and returns explicit scope, source-completeness and as-of information. Rows need stable building/unit/sale-attempt IDs, configured floor order, permitted buyer label, sale stage, all permitted action facts, team, deadline basis and exact destinations. Do not serialise the underlying broad dashboard input.
  • Reuse, with explicit gaps: the existing register is conveyancer-only, deliberately non-financial, and excludes fee actions. Do not remove its role guard to serve all roles. Reuse pure derivation, classification, permissions and ordering beneath reviewed developer/agent/conveyancer projections. Admin follows its existing internal rules; other roles retain their current access rather than inheriting Sales access from this pilot.
  • Dashboard/worklist agreement: derive both from the same complete, scoped action population. The existing internal dashboard response reduces its detailed item list; it cannot be used blindly as a complete sales feed. Keep stage counts labelled as units and action queues labelled as actions and distinct sales. A filter affects which rows match, not the underlying ownership of work.
  • Fees need a scoped read decision: the current get_agent_fee_portfolio path loads a portfolio and filters by building afterwards. That does not meet strict building-scoped operational loading. Review a bounded, building-specific read projection under existing authorisation, reusing current eligibility/calculation rules. Agent-visible fee facts need their own existing-access parity checks; never expose developer financials. Do not silently omit fees while labelling counts “all actions”. If parity requires broader backend work, stop at the contract gate and present a scope adjustment.
  • Navigation and old interface: keep the existing homepage, sales screens and links unchanged. Offer an explicit “Open existing sale file” handoff using the existing destination contract with building ID, unit ID, sale-attempt ID and task/version context. For the first pilot, open that file in a clearly labelled separate tab, retaining the original worklist tab. This avoids a legacy routing rewrite. Verify existing deep-link handling; any missing bridge is a reviewed, additive change, not a fallback to a same-numbered unit.
  • Read-side effects: do not mount detail workflows, comments or audit observers in the three new surfaces, or prefetch them. GET /api/sales/legal can expire authority; viewing comments can mark them read; opening a unit can audit the visit. Inventory those existing effects before testing an explicit legacy handoff against synthetic data. Business mutation testing is excluded from the pilot; the existing interface's permissions and behaviour remain unchanged.

Proposed target: a dedicated non-production Supabase development/test project, or a specifically approved isolated staging dataset, containing synthetic records only for this pilot. Existing repository documentation recommends separate development/production projects and notes that staging E2E tests can create actual staging records. It is not evidence that the current local configuration, project or accounts are authorised for this integration.

Before connection, record the exact approved project identifier, local application origin, migration/schema baseline, test identities and allowed operations. Verify the target fails closed if it points to production. Do not copy production buyers, documents, credentials or financial records. Do not run the existing broad staging seed automatically. Prepare a reviewed, repeatable manifest limited to the pilot's synthetic records, with cleanup limited to those exact records.

The manifest should include two buildings with G11, LG11 and 301, separate unit and attempt UUIDs, contrasting buyers/statuses; a third inaccessible building; single- and multi-building accounts; two organisations with the same role; two users in one organisation; appointed, unallocated and incomplete-appointment cases; and the mixed-action sale. Include restricted-role denials and changed-access cases. Use genuine test sessions and existing row/action policies, not a role selector or service-role browser client. Keep delivery sinks or outbound integrations controlled in the approved test environment so test activity cannot send real messages.

Start with intercepted/local contract fixtures for delays, failures and malicious scope mismatches. Only then exercise approved server/database reads. Inspect all HTTP methods and relevant database/audit effects: GET alone is not proof of read-only behaviour. No change to authentication, RLS, write rules, production notifications or production deployment is proposed.

5. Prevent cross-building publication

Each loader and in-memory snapshot must belong to a scope comprising the authenticated user, role, organisation, access revision, building ID and request generation. Detail handoffs additionally identify unit and sale attempt. Filters/page are included in the request key if they become server-side; initially they may be local only over a verified complete building result.

  1. On A → B, change route ownership and clear A's rows, counts, buyer labels, selections, errors and pending indicators before rendering B. B shows its own scoped loading state.
  2. Abort A, start B with a new generation, and publish only if both the owner/generation and the response's authenticated building scope still match. Abort alone is insufficient.
  3. Reject a late A success, failure or completion callback; it cannot change B's content, error or loading state. Apply the same rule to A → B → A so the first A response cannot overwrite the second A request.
  4. Keep caches and restoration separate for each tab and authorised scope. Store only worklist preferences and scroll, never protected rows or credentials. Known access changes/logout invalidate cached data and return state. Restored pages are clamped after counts change, and scroll restores after the correct scoped rows render.
  5. Publish required counts/rows together. Initial failure differs from empty success. A same-scope background refresh may retain a clearly stale snapshot only under the existing freshness/access contract; access revocation clears it. Cross-scope stale display is never permitted.

7. Evidence carried forward and remaining gaps

The capability/location checklist, data-loading assessment and refinement verification record remain the starting evidence. The prior pass recorded 33 browser tests, 71 targeted regression tests, lint/build success, 33 clean network logs and seven production 404 checks. Those checks were not rerun for this plan. They validate local fixture navigation/display and selected existing rules; they do not validate authenticated role projections, real in-flight responses or backend integration.

Still to close before the first pilot: the named environment/seed approval; role-safe read contracts including fees and permitted buyer labels; strict building scoping for the portfolio-backed fee source; complete internal action population; team-owned multi-action presentation and exact count semantics; data-load/cache race tests against real responses; and verified existing-file handoffs. The current prototype still uses fictional person-labelled ownership and single-scenario worklist actions; this plan supersedes that presentation contract without changing the prototype now.

Deferred capabilities remain in the checklist: complete authority/notice variants; document replacement conflicts; invoice corrections and payment voids; further deposits; full handover; commercial defaults and overrides; historical sale-attempt selection; comments/mentions/unread behaviour; notifications/global audit; fee portfolio design; and other portal modules. These are not implicitly covered by the three-screen pilot. The historical register-loading report also records a baseline visibility-listener test failure; re-establish its status during integration rather than treating all older suites as green.
