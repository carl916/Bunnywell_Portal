Data-loading assessment

The building-first structure can use the existing scope and cancellation patterns, but the current connected components cannot simply be mounted inside this read-only experiment. The next production step should be a scoped read contract review, followed by an explicitly approved integration phase.

Implemented now: local ready/loading/empty/error/unavailable fixtures only. Loading uses a five-second cancellable timer owned by the current URL. Changing building hides records immediately, cancels the old timer and starts a new scoped preview. There is no business-service fetch, RPC, file-storage request or backend change. Tab-local sessionStorage contains only worklist return preferences.

Scope and publication contract

  1. Key each response owner by authenticated user, role, organisation, access-membership revision, building ID, and (for details) unit ID, sale-attempt ID, section and document version where relevant. A building ID alone is insufficient.
  2. On a scope change, hide the old dataset synchronously, clear selection/drawers/confirmation targets, then request the new scope. Render the new building identity with loading or unavailable content, never old records.
  3. Cancel obsolete requests and also validate response scope and request generation before publication. Cancellation alone cannot prevent a late server result or a stale cache entry from being used.
  4. Publish related required records atomically. If required legal facts fail, do not substitute empty arrays or infer “no blockers”. Distinguish incomplete responsibility data from “no actions”.
  5. Keep each tab's operational context in its URL and each building's worklist refinements in tab-local state. Persist only filters, page and scroll under identity/access/building keys; never auth tokens, documents, buyer records or financial snapshots.
  6. Retain backend authentication/RLS and explicit ownership checks on every request. Client-side role wording, fixture selectors and route validation are not security controls.

State and recovery behaviour

StateExpected production behaviour / prototype demonstration
Initial loading or switchShow selected building identity and a scoped loading surface. No previous records, counts, buyer details or unit actions. Demonstrated by the cancellable local timer, including switching before the old timer completes.
Empty successShow that this building returned zero records. Separate from no filter matches; provide Clear filters only for filtered emptiness. Both variants are demonstrated.
Initial failureShow an error with retry and Change building. No zero counts presented as real results. Retry demonstration is a new local loading cycle only.
Access unavailable / revokedClear protected records, unit selectors and actions immediately. Retain safe context and a way to choose an accessible building. Known-building unavailability and malformed/inaccessible direct links are demonstrated separately.
Background refresh failureFuture integration should retain a clearly stale same-scope snapshot only if permitted, identify its age and restrict actions requiring current facts. This stale/refresh variant is not implemented in this prototype and remains a review item.
Mutation outcome / uncertain responseBusiness actions remain disabled here. Future integration must reconcile the affected task, worklist counts and identity using existing refresh contracts, preserve mutation and refresh errors separately, and avoid declaring success from stale data. It must not add financial gates to legal progression.

Before approving real-data integration

  • Confirm the source of authoritative work facts and role-safe DTOs for all three roles; the existing register route is conveyancer-specific.
  • Audit read-side RPCs, triggers, signed-URL routes, read receipts and audit observers. Reusing a method named GET or “load” is not proof of an inert read.
  • Measure current request count, payload size and time-to-first-useful-task per surface on an approved environment. Set budgets after measuring; no fresh live performance measurements were made in this pass.
  • Test role/access revocation, wrong-building records, changed sale attempts, late responses, same-scope refresh failures and mutation reconciliation against real contracts. The fixture navigation suite does not establish those integration properties.
  • Review the unchecked capabilities in the separate checklist before replacing any production route.
