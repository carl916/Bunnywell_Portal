# Targeted legal function region evidence

Application baseline: `9f423a0fe4d45204ac3ecf7d958b3d2b9a6d34d2`. Historical comparison: `docs/staging-function-region-ab.md`. The two new Git child commits alter only `vercel.json`, preserving existing crons. The B override is the exact source file `src/app/api/sales/legal/route.ts`; all other functions default to `iad1`. Both inherit the same Vercel preview environment entries, plus identical branch-scoped diagnostic flags. Application runtime and routing are unchanged.

`setup-evidence.json` and `deployments.json` identify the immutable previews and source comparisons. `environment-before.json` stores environment metadata only, without secret values. `candidate-inspection.json` records empty draft eligibility and excluded/protected units.

`preflight.json` is a read-only region gate. A legal GET without a sale intentionally returns 400 after authentication, before any sale work; method-only admin/unit GET probes intentionally return 405. These are region probes, not failed measured legal actions. Rentals GET probes run the actual read handler. The full `x-vercel-id` separates London ingress from function execution.

`samples.json` records eight paired rounds per profile/action/region, with per-request status, spans, execution region, cache headers, byte counts and static JS/CSS hashes. Cold clears Chromium's cache, not Vercel function state. Setup warms each preview; every run restores the same completed-sale UI state before cold/repeat navigation. Order alternates and mobile reverses the start. Inactive preview contexts navigate to `about:blank` to avoid competing background polling. Settlement excludes routine discussion polling; the quiet grace is not included in readiness or actual network completion.

Desktop is 1280×900. Mobile uses 390×844, 4× CPU slowdown, 150 ms network latency, 200,000 bytes/s download and 93,750 bytes/s upload. The readiness checks reproduce the earlier comparison: visible sale controls, rendered Exchange/Completion lists, parsed legal context plus two frames, or visible final authority preview. `verification.json` stores displayed-state/run checks and protected/unused-sale fingerprints around the read-only batch.

`summary.json` and `measurements.md` contain medians, IQRs, ranges and paired readiness differences. `details.json` adds paired complete-action differences, static asset comparisons, direct Supabase reads and mutation phases. Negative paired values mean B was faster. Concurrent server spans overlap: do not sum them. Remote database spans include network and service work, not just PostgreSQL execution.

`mutation-results.json` records one fresh authority issue per region, with exact consumed units and protected-record hashes. Preparation uses the existing reservation API, a synthetic reservation PDF, test buyer values and the existing staging test mailbox. Preparation and its Storage work are excluded from the authority measurement. Normalised legal snapshot hashes exclude sale/unit/plot and generated terms IDs, while comparing all legal terms, payment schedules, recipients, seller and approver. Both fixtures use the same future authority expiry. No sale is reset, and no measured mutation is repeated. Email timing is Resend API acceptance/receipt persistence, not inbox delivery latency. One pair cannot establish a mutation distribution.

`evidence-checks.json` validates sample counts, regions, configuration scope, displayed states, mutation receipts and protected-record integrity. `final-platform-verification.json` confirms that staging/production aliases and pre-existing environment metadata remain unchanged.

Reproduction scripts are in `scripts/diagnostics/`: `targeted-region-preflight.mjs`, `staging-targeted-region-ab.mjs`, `targeted-region-mutation.mjs`, `summarize-targeted-region-ab.mjs`, `targeted-region-details.mjs` and `verify-targeted-region-evidence.mjs`. They require locally configured authorised staging test credentials; none is persisted in this evidence. The mutation script requires `SALES_PERF_ALLOW_STAGING_MUTATIONS=1`, a clean completed read-only batch, fresh empty authorised drafts, matched snapshots and allowlisted recipients. It refuses to run if a mutation report already exists. Do not delete that guard or replay it on consumed fixtures.

No trace, screenshot, business response body, document content, signed URL, token or credential is saved. All measurements are from staging. The root Vercel configuration and production deployment are unchanged.
