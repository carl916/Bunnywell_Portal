Overall architectural health

The portal has a viable relational foundation: buildings and units, separate sale attempts, document versions and approvals, financial records, organisation access, and audit history. Partial unique indexes already enforce one active sale per unit, one current terms/version record, and one current agent invoice per milestone. Payment recording uses an invoice lock, a unique client reference and balance validation. Completion already has controlled upload finalisation and version-aware review operations. These are substantial assets to preserve.

The main weaknesses are permission enforcement at some older entry points, incomplete migration provenance, multi-request business transactions, and overly broad loading. They do not justify replacing PostgreSQL, Supabase, the accepted interface or the workflow model. They do justify a reviewed baseline and targeted database/API work before broader write integration.

The selected-building load remains 27 backend requests / 240.2 kB decoded. Five warm samples give a 1,265 ms API median; the usable dashboard median is 1,385 ms. Smaller screen-specific responses and fewer dependent requests can materially improve this. Simply batching queries is not sufficient: one tested snag-history alternative was slower.

No application source, database objects, business records, storage settings or UI were changed. Only this report and assessment evidence were added. Normal test-account sign-ins were used for read measurements; authentication may itself produce normal session/audit activity. Production was not accessed. The accepted design and working local Completion database remain preserved.

A — Resolve before completing further integration

Security and baseline corrections should lead the next work. The transaction findings are gates before enabling the affected business writes; they need not hold up unrelated read-only screens.

A1. Close exposed commercial write entry points and reconcile grants

Confirmed metadata/code issue: both save_unit_commercial_model overloads are SECURITY DEFINER, executable by anon and authenticated, and do not validate the caller, role, building access or supplied requester identity. The agent-fee and deposit wrappers retain explicit anon execution even though their migrations revoke PUBLIC/authenticated execution. Existing draft/legal triggers enforce lifecycle conditions, not a complete caller check. The audit actor helper permits a null actor, so it is not a substitute permission boundary. No write exploit was attempted.

Change: make these server-only operations explicitly server-only at every overload, including anonymous grants; add actor, active-profile and scope validation at the authoritative operation. Review default privileges so new application functions do not silently regain client execution. Preserve deliberately callable, validated RPCs. The existing payment recorder is a different case: its caller check and conveyancer building restriction are present and must remain.

Also remove unnecessary application-table TRUNCATE/REFERENCES/TRIGGER privileges from client roles. Both client roles currently hold TRUNCATE on 44 application tables. RLS does not protect TRUNCATE; this is excessive SQL privilege, not evidence that PostgREST offers a truncate endpoint. PostgreSQL RLS scope; Supabase function privileges.

Benefit / work / test: close routes around application permission checks; database ACL and function changes, with small server-call adjustments if needed. Test anonymous, inactive, forged-actor, wrong-building and wrong-organisation denial directly at RPC level; then authorised developer/conveyancer payment, commercial editing and legacy API regressions. Do this before publication, not as a cosmetic UI restriction.

A2. Correct snag write scope without removing approved public access

The authenticated Storage INSERT policy checks only bucket_id = 'snag-images'. It does not bind uploads to an active user, accessible building/snag or controlled path. The resident snag INSERT policy contains a.unit_id = a.unit_id, which does not bind the selected area to the submitted unit. UPDATE/DELETE of images are restricted to the back-office role helper; retain that restriction. The private snag-reports bucket has a separate SELECT policy allowing any authenticated user to read its files; three objects exist, and the policy is not report/building scoped.

Change: enforce active account, authorised record and controlled object ownership/path for uploads; correct the resident area/unit/building predicate and add relational protection (A4). Scope private report reads to authorised recipients/buildings or the reviewed server download path. Preserve snag-images public reading. Do not assume a private bucket alone supplies per-record permission: its RLS still matters. Storage access controls.

Benefit / work / test: prevent unrelated public uploads and cross-unit associations; database policies plus upload-path/API changes. Test valid developer and resident uploads, inactive and wrong-building users, forged paths, replacement/deletion and report access. No uploads, deletions, file downloads or policy changes were attempted in this review.

A3. Establish a reproducible baseline before relying on a clean rebuild

The repository contains 71 migrations; staging records 13. This is incomplete provenance, not 58 proven missing migrations. Local and staging largely agree on actual schema objects, but 12 function entries and 28 table-grant entries differ. The local replay supplies sales roles and ordering corrections outside the migration chain. The importer also has an incompatible completed-unit path: initialize_imported_unit_sale_status rejects units with sale history, while sales_legal_unit_guard requires a legally completed active sale before changing a unit to completed. The handed-over import first uses this completed path.

Change: reconcile final intended definitions, make role prerequisites explicit, and create a reviewed baseline including ACLs, triggers, Storage policies/buckets and required setup configuration. Define an audited legacy-state import path that can represent imported historical completion without weakening ordinary legal progression. Retain the existing spreadsheet importer and validate it against the new baseline; do not assume its historic success proves fresh-schema compatibility.

Benefit / work / test: repeatable environments and safe releases; database baseline and setup/import work. Rehearse from an empty disposable local database twice, compare object definitions and permissions, and test spreadsheet structure/floor ordering, historic statuses, reruns and interrupted import recovery. Preserve the conveyancer-payment fix and the existing local Completion instance throughout.

A4. Enforce record ownership relationships in the database

Separate foreign keys allow individually valid IDs to be combined incorrectly: sale → building/unit; area → building/unit; snag → area/unit/building; invoice → sale/document; payment → sale/invoice; document approval → a version belonging to that document. Current commands often check these relationships, but the schema is not a complete defence for other writers/imports. Fresh aggregate checks found zero mismatches in these six relationship groups, so this is preventive integrity work, not a claim of current corrupted records.

Change: add focused composite unique/foreign-key relationships or narrow constraint triggers where nullable communal locations and approval cycles need them. Keep stable UUIDs and explicit sale-attempt identity. Validate the five existing NOT VALID checks after data checks; no violating amounts, payment dates, void combinations or future reservation dates were found today.

Benefit / work / test: prevent same-numbered units and unrelated documents/payments from being joined across records; primarily database changes, with import/API error handling. Test negative cross-building and cross-sale combinations, valid communal areas, optional documents, historic records, replacements and delete behaviour. Add supporting indexes deliberately rather than copying every advisory suggestion.

A5. Make the remaining commands atomic and enforce transitions below the UI

Reservation approval currently updates the attempt, terms, document, unit and history through separate HTTP writes; several secondary writes do not inspect errors. Invoice approval updates document and invoice separately. Handover marks the unit handed over when the parent row is inserted, before key items, photos and meters finish saving. A later error can therefore leave a partial business operation. Snag changes use the existing change_snag RPC, but its patch allowlist and current RLS constrain records, not the full role/status transition rules; direct table updates remain another path.

Change: move each affected existing command into one authorised transaction with expected-version/status checks and idempotency. Reuse established validation/calculations and the working Completion approach. For file uploads, stage objects and finalise their references transactionally, with safe orphan cleanup. Enforce the existing snag role/transition matrix at the operation and remove bypass paths. Do not invent new workflow rules or financial gates for legal completion.

Benefit / work / test: no half-approved reservation or incomplete handover presented as complete; database operations and thin API adapters. Add failure-at-each-step, retry, stale-version, concurrent approval/payment and duplicate-submission tests in an isolated environment before enabling these writes. Existing Completion and payment transactions are the pattern to preserve.

A6. Introduce bounded read contracts and improve permission-query cost

The dashboard and sales worklist share a full-building payload; a direct Completion link also waits for that payload to resolve its row. Snags loads action facts and then another register dataset. Empty comments still require 13 backend calls because their scope check reloads Completion metadata. Current RLS plans repeatedly evaluate role/access helpers for each row. Exact-count checks detect truncation or changed counts, but they do not provide a consistent database snapshot across HTTP reads. Count-stable edits can still mix related facts; use a consistent statement for coupled facts or explicit revision validation/retry.

Change: give the existing read service distinct summary, paged worklist and exact-record projections; share authorised facts and pure work classification. Consolidate redundant reads and request-local access context while retaining end-of-request access revalidation. Optimise row-independent RLS helpers to run once per statement where valid, and use scoped joins/sets for per-record permission checks. Never achieve the saving by bypassing RLS with a broad service-role read. RLS performance guidance.

Keep ordinary reads inert. The legacy GET /api/sales/legal calls sales_legal_expire; viewing legacy conversations can mark comments read, and unit-open tracking writes separately. The new read-only workspace correctly avoids these. Derive expired state during reads and perform any required persistence at an explicit command/job boundary with existing audit semantics.

Benefit / work / test: faster initial task access and less data transfer; API projections and selected database policies/indexes/read functions. Repeat the measurements below after each change, with full role/scope and late-response tests. Pure data reads can be shared between old and new screens; a second workflow engine is unnecessary.
