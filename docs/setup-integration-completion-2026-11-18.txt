Architecture

The restored Setup was a second application entry point inside the same Next.js
deployment. /setup mounted the legacy portal with a separate session lifecycle,
building state and horizontal navigation. Crossing to /workspace used a full
document reload. The workspace also rendered sign-in before persisted-session
verification finished, which caused the login flash.

Setup now mounts inside ConnectedWorkspace alongside Sales, Snags and Dashboard.
It shares the sidebar, breadcrumbs, mobile navigation, building context, session
and command boundary. Internal navigation retains the same document. /setup and
legacy screen URLs redirect into the shared workspace; no legacy portal is mounted.
Nested Setup URLs retain their building and panel on refresh.

Authentication distinguishes restoration, verified access, transient failure and
definitive rejection. Rate limits offer retry; invalid sessions reach sign-in.
No cosmetic delay or CSS concealment was used. Dirty forms warn before navigation.

Backend

The audit found no restoration migration in the staging ledger. The regression
reopened old browser/API write paths while the newer transactional Setup contract
still required fictional/test records. There was no complete historical policy
snapshot to prove the absence of every earlier manual change.

The following approved migrations were applied only to staging:

They update Setup context/commands for ordinary administration, lifecycle
consistency and transactional audit events. No tables were reset or reseeded;
no older migrations were replayed; no RLS policies were changed.

The command boundary retains active actor/role checks, service-role-only RPC
execution, exact building ownership, record locking, expected-version checks,
request receipts and retry conflict detection. Allocation and user access reuse
the existing validated RPCs. Commercial defaults save atomically and retain
established sale terms. New units start unreleased and outside the rental
portfolio, without automatically starting a sale.

Ordinary Setup no longer asks users to create fictional/test records. Existing
private staging registration remains for Snag eligibility and correspondence
capture, including ordinary new buildings. Existing test journeys are retained.
Sales contact routing is separate from user/building access. Account creation
and invitations use a bounded, validated server Auth path.

Functionality and cleanup

Integrated features: building details; floor/unit/area structure and configured
floor ordering; unit types, size and parking; lifecycle/PC/access-request settings;
delivery team; commercial defaults and deposit timing; sales contacts; unit sales
availability and rental participation; audit streams/filtering/pagination; users,
organisations, role/building/flat access, account status and access-request review;
invitation/password recovery handling.

Removed the legacy ProductionPortalApp mount, duplicate BuildingControls and
SetupControls, their obsolete WiderViews exports, and the old admin user route.
Legacy admin/allocation mutation routes are blocked at the workspace boundary.
The public access-request endpoint remains for resident onboarding. Shared domain
helpers and unrelated services remain where needed; this was not a repository-wide
deletion of every historical file.

Destructive unit and organisation deletion are not exposed in the new Setup UI;
empty-floor and unused-area removal retain backend safeguards. Unit commercial
workflow remains in Sales. Approving a new resident request requires first creating
or inviting its account; approval merges access for an existing resident. These
are explicit limitations rather than claims of identical legacy feature coverage.

Accepted Sales, Snags and Dashboard interfaces were not redesigned.
