Commercial terms and data integrity
- Reservation has View commercial terms and a developer/admin-only Amend commercial terms action. Amend opens the existing commercial editor; no parallel editor or submission service was added.
- Submitted reservations stay locked. Approved, active, unexchanged reservations can be amended by a developer/admin with an explicit reason and confirmation. Backend checks enforce role, actor, scope, approval metadata, sale state, current terms and defaults.
- Approved amendments create a new existing unit_sale_terms version, retaining original commercial values and approval metadata on the previous version. Audit records contain the reason, actor, before/after terms and before/after payment schedules. The original reservation PDF and approval record are preserved.
- The current schedule continues to use the existing save operation. The schema permits only one schedule row per sale/sequence; previous schedules are preserved in the amendment audit rather than adding a second schedule schema.
- An unwithdrawn authority, including an expired one, blocks amendment. The developer must explicitly withdraw it using the existing action, then amend and issue a fresh authority. Existing stored authority content is never rewritten. Stale signed previews are rejected if terms or recipients change.
- Existing invoice or deposit-receipt records block this amendment route, preventing silent recalculation of recorded financial work. Those cases require a separately reviewed financial correction; no new financial correction workflow was introduced here.
- One staging migration, 20261119143503_authority_review_commercial_amendments, updates the existing workspace_sale_operation function and restricts three legacy commercial-save function overloads to service_role. Those legacy entry points previously permitted direct client calls; the integrated server is now the required entry point. No tables, columns, existing data or authority records were migrated.
