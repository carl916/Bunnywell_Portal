Result

The integrated Reservation page now submits entered details, commercial-terms confirmation and the selected signed PDF through one Submit reservation action. Save reservation PDF and Save draft have been removed from this workflow. The shared styled upload surface still provides Replace and Remove before submission.

The form explains missing buyer/contact/solicitor/date details, unchecked terms and missing PDF. File checks cover PDF name/type/signature and the existing 2 MiB workflow limit. Submission displays a processing state and blocks repeat clicks. Failed requests retain the entered details and selected file; uncertain retries reuse their submission reference.

After submission, the existing Reservation record, Reservation form and Review reservation presentation are retained. The upload editor is hidden. Reviewers can explicitly return a reservation for revision with a reason; permitted submitters then select Revise reservation. Saved details remain visible while it awaits revision. A revised PDF becomes a new version only when the revision is submitted successfully. Approved reservations retain the existing approval and correction rules; this change adds no permission to silently replace or reopen an approved reservation.

Existing saved drafts remain readable and can be submitted with their existing saved PDF. The underlying legacy draft command remains for compatibility and existing test journeys, although no new Save draft action is offered in this workflow. Historic PDF access, current-version approval, submission metadata and audit events use the existing contracts.

Backend and integrity

The implementation extends the integrated workspace upload service and reuses workspace_reservation_file, workspace_reservation_command, commercial-term calculation and payment-schedule generation. The unused standalone reservation upload branch was removed. Notice and invoice workflows retain their existing paths.

Two service-only RPCs coordinate uploads: workspace_reservation_upload and workspace_reservation_submit. They use the existing private operation_receipts table. There are no new tables, RLS changes, bulk data updates, resets or deletions of existing test data.

A database transaction was necessary to commit the PDF version, reservation details, commercial terms, submission status and audit events together. The previous independent calls could leave only one half persisted. Storage bytes are uploaded first to a unique, tracked path; finalization verifies the stored object and runs the existing file-registration and reservation commands within one transaction. The same sale lock resolves commit versus cancellation before cleanup. A lost successful response returns the committed receipt and never deletes the submitted PDF. Identical retries are idempotent.

Recovery limitation

Storage and PostgreSQL cannot share a native transaction. Known failed attempts are cancelled under the database lock and their staged file is removed. If the outcome or deletion cannot be confirmed, the intent remains durably tracked and is not presented as submitted. A subsequent attempt for the same actor/sale cleans aborted paths and cancels abandoned prepared intents older than one hour. No background cleanup job was added; an abandoned upload can therefore remain stored until that actor retries or an operator performs scoped cleanup. Existing submitted/approved versions are never cleanup targets.
