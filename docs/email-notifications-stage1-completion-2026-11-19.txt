IMPLEMENTATION
Setup has an Email notifications tab with all 16 requested event rows, the three
recipient-role checkboxes, one Save changes action, and a separate Mentioned in
a comment switch. All requested defaults are present. Ordinary comments default
to no roles; mentions default on. The recipient label is People tagged in the comment.
The screen explicitly states that settings are system-wide, apply across every
building, and take effect when delivery is connected.

One private singleton configuration stores role overrides, the mention switch,
version and audit attribution. One SQL event catalogue defines stable identifiers,
labels and defaults. Missing event overrides inherit catalogue defaults; explicit
empty arrays stay empty. Saves merge known submitted rows, preserving omitted
rows when an older client encounters a newer catalogue. Unknown event identifiers,
unknown roles, duplicate roles and malformed settings are rejected.

The existing verified workspace session and workspace_commands.setup_actor enforce
active admin/developer settings administration, including the verified audit actor.
Only service_role can execute the public settings/selection RPCs; the private
table has no direct client access. Saves are atomic, version checked, idempotent
by request ID, and recorded in the Setup audit stream with before/after values.

Server entry point:
src/lib/workspace/email-notifications-server.ts
resolveEmailNotificationRecipients(eventId, saleId, commentId?)

It loads current persisted preferences and trusted candidate facts from the
service-only workspace_email_notification_context RPC. Candidate access reuses
can_access_sale, sales_building_access and sale_discussion_access. Both ordinary
comments and mentions require visibility of the exact stored comment on that sale.
Inactive users, blank addresses, unavailable/redacted sales and mismatched comments
are excluded or rejected. Explicit tags come from the stored comment mention_ids.
Building sales-contact addresses do not grant portal access or become user recipients.

Developers includes admin and developer profiles, following the existing internal
Sales role convention. Developer representatives do not gain Sales access. The
current schema stores one profile role per user. The selection contract accepts
multiple role memberships and deduplicates by user ID; it does not introduce a new
multi-role administration model. Results retain saleId, commentId, eventIds and
reasons, combining ordinary-comment and mention eligibility into one user item.
No send, queue insertion, trigger or batch scheduler is connected in Stage 1.

STAGE 2 HANDOFF
1. Mentions: reuse sale_comments.mention_ids, sale_comment_write validation and
   sale_mention_notifications identities. Existing notification rows also support
   in-app mentions; do not repurpose or disable that inbox using email preferences.
   Current staging commands.ts always passes p_mentions:[] and command-fetch.ts
   explicitly permits only empty mentions. Connect a validated tag picker and
   narrowly update that command boundary. Use the stored comment ID when enqueuing.
   Some legal workflow requests generate in-app notification rows independently
   of explicit tags; map these to their workflow events, not comment_mentioned.

2. Reservation approval: connect the committed approval event from
   workspace_reservation_command (core-commands.ts) to reservation_approved.
   Reuse its transaction, actor/access checks, stale-version handling and request
   receipts. The inspected approval path has no outbound approval email sender.
   Do not add a browser-side send or replay notifications on command retries.
   Submission uses the existing reservation submission commands; hook the committed
   workflow event once, including resubmission, rather than every upload/draft save.

3. Existing legal mail: src/app/api/sales/legal/route.ts sends through Resend with
   sales_legal_prepare_email, sales_legal_dispatch, immutable saved HTML/text and
   the sales-legal/<emailId> idempotency key, including uncertain-delivery retry.
   Reuse these delivery/reconciliation principles, src/lib/email/layout.ts and
   src/lib/sales/legal-email.ts. Existing resolveSalesRecipients routes legal
   correspondence to a conveyancer organisation's shared_system_email, optionally
   CC'ing the sales-agent organisation. That is distinct from configurable portal
   user alerts: replace it for new workflow alerts, while deliberately deciding
   whether formal legal correspondence continues to require its existing recipients.
   The legacy /api/sales/legal sender is blocked by the staging workspace proxy.

4. Five-minute batching: there is no existing sales batch outbox/dispatcher.
   Add a durable transactional outbox keyed by source event and recipient, with
   explicit claims, retries and provider idempotency. Group per recipient over
   five minutes; combine comment_added/comment_mentioned by recipient + saleId +
   commentId, retaining mention prominence. Recheck current settings, sale access
   and comment visibility before dispatch so revoked access cannot leak content.
   Do not infer events by periodically diffing mutable sale snapshots.

5. Snag digest: src/lib/digests/snag-digest.ts and /api/cron/snag-digest contain
   layout, run-receipt, enable/disable, recipient-allowlist and dry-run examples.
   Its daily 07:30 London digest_runs key is not a five-minute sales outbox, and
   its sender lacks per-item provider idempotency. Reuse the safeguards/patterns,
   not its schedule or recipient resolver. Keep staging capture routing enforced
   server-side when introducing any new transport or cron endpoint.

6. Links: portal-url.ts currently emits legacy screen=sales/conversation links;
   the staging proxy redirects / to /workspace. Stage 2 needs current workspace
   building/unit/sale/comment deep links, with sign-in preserving the destination.
   Retain the trusted configured-origin validation, but update/test the path builder
   for this integrated application before sending new notifications.
