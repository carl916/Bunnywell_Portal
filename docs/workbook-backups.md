# Production workbook backups

The existing production backup workflow generates an operational Excel package every night after the database dump and Storage mirror finish. It starts at **02:17 UTC** (02:17 GMT / 03:17 BST), and can also be run from GitHub Actions → **Supabase production backup to Dropbox** → **Run workflow** on `main`. Changes to the exporter trigger a run on merge to `main`.

## Opening a backup

In Dropbox, open `Supabase Backups/bunnywell-portal-production/workbooks`.

1. Download and extract **Latest.zip** completely. The workbook needs the accompanying `files` folder.
2. Open **Bunnywell.xlsx** and start with **Start here**, **Needs attention**, **Sales progression** or **Snags**.
3. **Documents** contains links to the retained original PDFs, images, reports and legal correspondence. These links work offline. Live sale links open the authenticated portal record. External links are labelled and listed as exceptions.
4. To continue work during an outage, copy **Working log.xlsx** to a separate working folder. Record the sale/snag ID, action, owner, outcome, next deadline and supporting evidence. Nightly exports never overwrite that working copy.
5. When the portal is available, reconcile those actions against current records before entering them. Workbook edits do not change the portal or grant legal authority.

The master package contains buyer and contact information. Use the existing restricted Dropbox backup destination. Do not share the master package with external parties.

## Contents and interpretation

- All units, grouped by building and configured floor order, with active sale stage, next action, responsibility, authority expiry, completion deadline and approval of the **current** document version.
- Buyer/solicitor details, all commercial terms versions, payment schedules, locked exchange deposit expectations, receipt revisions, invoices, payments and outstanding invoice balances. Expected amounts are separate from receipt evidence; voided payments and superseded receipt confirmations are explicitly labelled.
- Snags, assigned parties, deadlines, suggested next actions, full descriptions, comments/status history and original photographs.
- Current and superseded non-redacted sales document versions, saved snag PDFs and recipients, handover signatures/photos, key details and meter readings/photos.
- Contacts, source table counts, snapshot timestamp and a manifest with SHA-256 checksums and original Storage references.

The workbook uses UTC timestamps and the database dump from the same backup run. It is a snapshot, not a live view. The Storage mirror runs after the dump; these are not a transaction spanning both services. Missing referenced files or a mismatch against a recorded file size/checksum stop publication. A retry captures a new snapshot.

Downloaded snag PDFs are saved centrally when generated by users with report-sending permission; this saves a copy without emailing anyone. Existing download-only roles retain their current permissions. Earlier PDFs that were never uploaded cannot be recovered from the database. Third-party external URLs are indexed but their contents are not downloaded. Redacted versions and temporary upload-session objects are excluded from the operational package. Unlinked Storage objects remain in the technical Storage backup.

## Publication, retention and alerts

Each dated `workbooks/<UTC timestamp>` folder contains an extracted `package` and a self-contained **Bunnywell.zip**. The workflow checks each uploaded file and downloads the archive to compare its bytes before replacing **Latest.zip**. Dropbox replaces that single file as a complete object. Export or verification failures before that step preserve the previous Latest package. A verification failure after the replacement still fails the workflow and leaves the dated archives available for investigation.

Dated workbook packages are retained for **90 days**. Latest is retained independently. Each package owns its file copies, so changes or deletions in Supabase do not break that retained package. The database archives (90 days), current Storage mirror and replaced/deleted Storage history (365 days) continue separately for technical restores. Keeping both the extracted package and ZIP uses additional Dropbox capacity.

At **07:00 Europe/London**, an independent Vercel cron checks GitHub for a successful production run whose workbook publication step completed that day. A missing, failed or uncheckable backup sends an alert to **info@bunnywell.co.uk**, using the existing Resend configuration. Two UTC schedules cover GMT/BST, with a London-time guard and a daily email idempotency key. GitHub workflow failure notifications remain available as a second signal. The check verifies the publication result recorded by GitHub, not a subsequent manual deletion from Dropbox. If Vercel or email delivery itself is unavailable, inspect GitHub/Vercel failures directly.

Required existing secrets: production database and Storage credentials plus the Dropbox rclone configuration in GitHub; `CRON_SECRET`, `RESEND_API_KEY` and `DIGEST_FROM_EMAIL` in Vercel. `BACKUP_ALERT_EMAIL` can override the default recipient. No new database migration is required. Neither workbook generation nor publication writes to the production database.

## Development and recovery checks

Use Node 24 and run `npm ci`, `npm run test:backups`, and `npx tsc --noEmit`. Run `bash scripts/backups/test-publication.sh` to exercise publication success, a failed remote file check and a corrupt archive download using local transport stubs. Both failures must preserve the previous Latest package. These checks also run in CI.

For an authorised local dry run against an extracted database backup and Storage mirror:

```text
node scripts/backups/generate-workbook.mjs --dump=/secure/data.sql --media=/secure/storage/current --output=/secure/new-package --snapshot=2026-10-07T02:17:00Z
```

The output directory must be new and empty. Keep production test data and generated packages outside Git. Do not upload them as public GitHub artifacts. Tests use synthetic records to exercise current-version approvals, deposit corrections, voided payments, missing files, safe relative links, redaction, formula-like text, DST and failure alerts.

For a staging validation export, supply its `--projectRef` and `--portalUrl=https://staging.bunnywell.co.uk` explicitly and use a separate local output folder. It is labelled as a validation snapshot and its live links point to staging. Do not publish that package to the production Dropbox destination or add a nightly staging backup.

After a failed run, inspect the failing step, resolve the missing data/credentials or service failure, and run the workflow again on `main`. Use a fresh run rather than rerunning an old commit after an exporter fix. Before using a package for continuity, extract it, open a document through the workbook, check its snapshot date and keep an untouched copy.
