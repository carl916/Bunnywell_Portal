RESIDENT DATA AND ACCESS

user_unit_access.access_type stores the relationship label for a unit assignment.
The database permits multiple labels on the same user/unit, including legacy
Representative. Effective unit access uses assignment membership; neither type
field is a role permission switch or a routine sales notification selector.
Database/source inspection found the type values in saving, access-request
approval, profile display and audit history, with no type-dependent RLS policy.

The UI groups legacy rows into one flat selector. Saving retains ALL existing
access-type rows for each retained flat, including Representative, even if the
user-level type changes. New flats use the selected user-level resident type.
Removing a flat omits all assignments for that flat, preserving the others.
A live transaction exercised unchanged save, legacy Representative plus a second
label, adding a flat and removing a flat; assertions passed and the entire test
was rolled back. Existing user data was not left changed.
