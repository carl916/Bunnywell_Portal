ROOT CAUSE
Delivery team generates a candidate assignment ID on save. The database command
looked up and upserted by that ID, while staging also enforces a unique tuple of
building_id, organisation_id and role_on_project across active AND inactive rows.
Re-selecting an earlier organisation therefore attempted a duplicate insert.
Database logs confirm tuple-uniqueness failures at 08:56:12 and 08:56:22 UTC.
The original operation was already transactional; the identity lookup was wrong.
The global Setup notice also survived navigation to unrelated tabs.

ASSIGNMENT FIX
The command now finds the existing unique assignment tuple and reactivates that
record, or inserts only for a first assignment. It locks the building before
reading the current holder, switches the two single-holder roles atomically and
returns the actual assignment ID. Failures roll back the outgoing deactivation.
Unchanged saves do not update the row or add an audit-history entry. Supporting
trades and other multiple-holder roles retain other organisations.
New clients send the observed holder ID and timestamp to reject stale replacements.
Existing submission receipts still make duplicate requests idempotent.
Tuple uniqueness, both active-holder indexes, the existing administrator check,
service_role-only function execution, and building read permissions are preserved.
Success refreshes Setup reference/building data, used by Delivery team and Overview.

FEEDBACK AND LAYOUT
Success messages use the actual database outcome, including both organisation
names on replacements. Failed replacements name the attempted organisation and
the holder retained after rollback; database details remain in server logs.
Success notices sit within the active building section, expire after five seconds
and are hidden immediately when the tab, panel or building changes. Errors use
the portal's error colour and an alert role, and remain until retry or navigation.
Email notifications remounts on building change to discard local feedback.

All seven building tabs use shared spacing and widths. Building details has paired
desktop fields, a mobile stack and separation around Notes and Save. Lifecycle
groups the 220px PC date, confirmation and calculated dates, with a separate
resident-access checkbox and explanation. Delivery team pairs role/organisation
and lays out current role, organisation and its labelled Remove button together.
Sales setup, Sales contacts and Structure share field spacing; Structure pairs
related fields on desktop and stacks them on mobile. Overview sections are spaced.
The notification matrix retains its system-wide event-by-role model, uses 13px
event text, 16px visible checkboxes, reduced row padding, 44px click targets and
visible keyboard focus. Mobile labels still identify each role alongside its event.
