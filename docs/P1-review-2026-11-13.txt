P1 findings: root causes, changes and status
------------------------------------------
BW-004 — FIXED. This was principally a React subtree remount, not a browser
document reload. Unchanged SIGNED_IN events emitted on tab visibility triggered
an unconditional lifecycle reload. A fresh Session object recreated the reader
and workspace and cleared the rendered snapshot. Stable, revocable credentials
now rotate tokens without replacing the reader. Focus still verifies getUser,
the current session and the authoritative role/building catalogue. Identity,
revocation and access-revision changes invalidate protected state. Same-scope
Sales refreshes preserve mounted content; Setup/Snags/Buildings use explicit
refresh and their own successful mutations, so idle focus cannot discard forms.
A final regression caught and removed a remaining refresh-key remount on Snags.

BW-020 — FIXED. Document-slot keys included the parent refresh counter, so
uploading either PDF remounted both slots. Slots now have stable sale/type keys,
independent pending state and request IDs, and clear only their own successful
upload. Failed/conflicting uploads retain the file for retry. Expected version is
captured when selected, protecting against replacement of a newer version.
Files remain in component memory, never browser storage. Step changes and real
page departure warn about pending files; sign-out/security changes take priority.

BW-007 — FIXED. Changing a filter recreated the reader request even though the
server had already computed the complete authorised building projection. Before
the fix a filter issued a new worklist request; after it, the tested subset filter
issues none. A complete projection of at most 200 rows is cached in memory for
30 seconds, scoped by account, role, organisation, access revision and building.
Larger/incomplete projections continue server reads. Counts, pagination, URL/back
navigation and configured floor order are preserved. Mutations, explicit refresh,
security invalidation and expired entries bypass/clear the cache.

BW-010 — FIXED. The record width cap left unused space; panel sizing used the
parent's lower edge and overflow:hidden could clip the composer. Records now
use available width, with a permanent sticky desktop right column and usable
scrolling. Composer/actions fit laptop and short desktop viewports. Mobile stacks
the panel. No drawer or default collapse was introduced.

BW-013 — FIXED. A hardcoded documents default selected step three. Fresh visits
now select Authority; explicit task links survive refresh. Notice-authority
action links are routed to Completion, independently of exchange-authority links.

BW-018 — FIXED. The editable notice form had remained dominant after recording.
A prominent recorded state now shows issue date, contractual due date, recorded
actor/time where available, current filename/version and private PDF action.
Replacement is secondary and deliberate. Wording says integration test recording,
and explicitly does not claim real delivery or legal service.

BW-019 — FIXED. Successful uploads now show their filename and success message,
current version/date, and "Uploaded — awaiting approval". Approval still depends
on approval of that exact current version; upload alone does not imply approval.

BW-022 — FIXED. Core and correction controls were mounted across all Completion
tasks. Authority, Notice, Documents and Legal now contain only their own actions.
Legal-completion entry is absent until both current required documents are
approved. The compact progress summary remains visible.

BW-023 — VERIFIED EXISTING CAPABILITY / SAFEGUARD, WITH CLARITY IMPROVEMENT.
The current backend and receipt component already support authorised conveyancer
recording/correction on enrolled fictional exchanged sales, beside expected,
received and outstanding amounts. Actual isolated-adapter tests exercised receipt
recording, retry and correction. Imported reference sales remain protected; their
deposit position now remains visible with a clear reason recording is unavailable.
Missing locked source amounts still require reconciliation rather than guessing.

BW-025 — VERIFIED EXISTING CAPABILITY / SAFEGUARD. Developer editing already
works for enrolled fictional for-sale units and was exercised through the actual
adapter, including stale-edit rejection. The editor is a deliberate action below
the restored summary. Imported records were not enrolled or made writable.
Operational rollout for real imported records is a separate decision below.

BW-026 — FIXED. The integration detail adapter returned a sparse raw field list.
It now supplies Developer / Agent / Buyer summaries from authorised current terms,
using the existing commercial-model and payment-schedule functions used by the
accepted product. This includes developer proceeds, milestone fees/net/VAT/gross,
reservation-fee and agent-contribution deductions, and buyer payments/timing.
Missing values stay unknown. Drafts are clearly labelled; penny rounding is
explicit. The developer figure retains the established model's treatment of VAT
and other costs, with an explanatory note. Existing editing and audit paths remain.

BW-027 — FIXED GENUINE READ/SCREEN DEFECT. For non-internal users the detail
adapter filtered out unapproved terms, hiding for-sale draft terms. The page also
requested a developer-only commercial controls context for conveyancers. The
commercial view now reads existing buyer terms within exact building/unit/sale
access, with a server-side column allowlist and a buyer-only response. It omits
developer fees, margins, commission and private narrative. No RLS widening was
needed: the existing SELECT policy uses can_access_sale_attempt. Missing terms
and denied record access are distinct states. No developer-only control request
is made from the conveyancer commercial view.

Authentication decision and imported-record release
--------------------------------------------------
The app uses Supabase email/password authentication (@supabase/ssr browser
sessions). Integration Auth and data are in project mmwzhzziqvjbsphrkbqr; staging
uses vxkpvdtrldwwqiddoyof and production zxgezoiazsubopqhqhim. Integration has
fictional review identities, separate auth.users UUIDs, profiles, organisations
and building/unit assignments. Server validation plus RLS and action permissions
remain authoritative. Vercel Authentication protects the deployment separately;
passing that outer gate is not application sign-in.

The pinned integration Auth configuration disables signup/anonymous access/SMS
and routes email/SMS hooks to integration_controls.block_delivery. The new code
does not alter it. Existing capture-only legal correspondence and private evidence
rules remain. There were no invitations, emails, SMS, payments or legal notices.

Decision for Carl:
1. Keep fictional review accounts (recommended while testing isolated workflows).
2. Provision specifically approved reviewers as separate integration identities,
   with explicit role, organisation and building assignments and an agreed access
   process that preserves blocked external delivery. The same email in two
   projects is still two independent identities, not a shared staging session.
Pointing integration at staging Auth/data or accepting staging tokens would cross
the isolation boundary, require access/data mapping and a separate reviewed
environment plan. Nothing in this round does that or enables invitations.

Imported-record rollout must not relabel real buyers/records as fictional test
journeys. Before operational writes: inventory the approved record cohort and
owners; take recovery exports; reconcile unit/sale stages, terms, deposit sources,
private files and legacy timestamps; validate role/building assignments and RLS;
design an explicit operational activation path separate from fictional enrollment;
dry-run with audited before/after comparisons; obtain approval for the cohort and
delivery policy; then release a small monitored batch with rollback/reconciliation.
No such activation or migration was performed here.
