Return to sale now requires an active reservation with a recorded developer approval timestamp and approver, and an approved pre-exchange workflow status. Draft/no reservation, submitted, awaiting approval, queried, rejected, exchanged and completed reservations do not expose the action. Both the legacy completion timestamp and the legal completion timestamp block returning a unit. The database checks the current row while holding its existing lock, independently of PDF presence or populated buyer details.

The Corrections and exceptions disclosure remains collapsed by default and disappears when there is no permitted action. It uses the existing card and field styles with 18px gaps, separate checkbox spacing and a processing state. A native confirmation dialog explicitly states that the current sale attempt will end, a new attempt will be created, buyer contacts and active documents will be redacted, and audit history will be retained. Reason and checkbox remain required. The integrated backend now also requires confirmed=true as a JSON boolean.

The rejection path was inspected and left unchanged. Rejection keeps the active attempt available for correction, leaves the unit For sale, records the reason, and resets commercial confirmation. Revise reservation retains the entered buyer details and supports PDF replacement and resubmission. This recovery path was exercised through developer approval on both the local candidate and deployed staging.

The previous inconsistency was that both the disclosure and the return helper accepted pre-approval states. The context also omitted approval metadata. The correction reads the real approval fields and restricts the existing helper; it does not infer approval from a document. Existing active approved/pre-exchange staging records had approval metadata, so no backfill was needed. The schema also contains both completed_at and legal_completed_at; both are now respected.

Backend changes are limited to definitions of return_pre_exchange_unit_for_sale and workspace_sale_operation. No tables, columns, policies, approval contracts, PDF submission contracts or rejection contracts were changed. Existing service-role execution permissions, building access checks, transaction boundaries, idempotency receipts, buyer/document redaction, terms supersession and audit creation remain in place.
